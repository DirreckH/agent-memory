Agent Memory API · V3.1 时间感知检索 + 双通道查询

时间感知检索方案说明

本地可部署的长期对话记忆服务：SQLite 持久化 + ONNX 语义召回 + 可选 LLM 索引增强。 方案的核心命题是——让"用户上个月说过不吃什么""搬家之前住哪"这类时间限定查询可被正确检索， 无有效时间约束时保留原有打分路径。 常见表达先由规则解析，复杂抽取与查询扩展独立；时间计算由确定性函数执行， 严格模式按确认窗内、时间未知、窗外补充分组排序。

初版基线：59a73ad；当前行为按工作区修订 走查：2026-10-03；真实 LLM 验证：2026-10-04 回归实测：224 passed（含本机 HTTP）
摘要 问题定义 架构与数据流 用例走查 抽取与解析分层 软打分 程序化防御 双通道查询 实证 工程底座 质量保障 边界与披露

0 · 摘要

一句话方案与核心结果

设计主线：“昨天、今天、本月、过去三天”等常见表达先由规则解析，复杂表达由独立 LLM 入口抽取； 模型不换算日期，绝对窗口由 app/temporal.py 计算，检索排序由 app/service.py 执行。 LLM 约束须通过字段、原文证据及方向校验，事件记录还需达到锚点匹配阈值。 严格模式先分组后排序，增大 top_k 不会让补充记录越过窗内证据。 TEMPORAL_MODE=off 旁路时间处理；QUERY_DUAL_CHANNEL=false 仅关闭双通道融合。

1 · 问题定义

时间序列推理检索，难在四个具体的地方

评测场景是长期多轮对话：同一主题、不同时间点的记忆共存于库中 （"上个月报了陶艺课"与"这周开始玩陆冲板"），查询带时间限定（"最近一周的新爱好是什么？"）。 纯语义检索对这类查询是结构性失明的——不是调参能解决，而是打分函数里根本没有时间这个输入。

挑战 1

语义向量对时间盲

同内容、不同时间的两条记录语义分完全相同。旧实现的平局由 created_at 升序决定——旧记录排前面，恰好把时间限定查询答反。

A/B 数据中 off 模式 15 例里 12 例目标未排到第一，9 例被同主题分心项压过。

把时间匹配项 time_match 作为第三路加权分数引入，窗口内得 1.0、窗外按半衰期衰减。
挑战 2

LLM 不知道现在几点

若让 LLM 把"最近三个月"换算成绝对日期，它必须先知道当前日期——而评测契约里模型拿不到可靠时钟，猜日期必然系统性出错。

提示词明令禁止换算；LLM 只输出相对约束结构。代码优先使用显式查询时间，否则按回放 / 实时模式确定参考时间并解析窗口。
挑战 3

LLM 会幻觉时间约束

查询根本没有时间含义时，模型仍可能"贴心地"输出一个时间窗口，把无关查询强行按时序重排。

schema 逐字段校验、数量与方向对应原文、事件短语证据核对；事件定位另设匹配阈值。仅命中时间信号正则不足以采纳 LLM 约束。
挑战 4

大量记忆没有时间戳

评测消息常不带 timestamp。若时间未知即惩罚，这批记录会在所有时间查询中被错杀。

消息时间缺失时保持未知，不回退入库时间。已有有效窗口时，未知记录的时间项为 0.5，时间过滤保留，但仍受最终相关度阈值约束；回放缺少参考时间时放弃相对窗口。

2 · 架构与数据流

两条链路：写入先行落盘，检索可降级

9 个模块各司其职。时间感知层（绿色）与查询表达层（蓝色）只出现在检索链路，且都可整体旁路：

Add 链路（POST /set）—— 契约：持久化完成且可检索后才返回 200

1
Schema 校验
双协议解析；MAX_MEMORY_CHARS 上限
→
2
幂等占用
claim_request：request_id + payload_hash，冲突 409、重复返回幂等成功
→
3
LLM 索引增强（可选）
V2 提示词生成事实保真的辅助索引文本；失败按 LLM_FAILURE_MODE 回退或 503
4
向量化
FastEmbed / ONNX 多语言模型，L2 归一化；内容渲染为 [user | 时间戳] 参与嵌入
→

向量 BLOB + source_timestamp（缺失保持 None）+ 增强文本，单事务提交

Search 链路（POST /get）—— 契约：只返回记忆证据，不生成答案

1
时间抽取与校验
先捕获查询时刻；常见规则优先，复杂表达交给独立 LLM；只读原查询并核验证据
→
2
查询扩展（可选）
仅生成检索辅助文本；独立开关，不改变上一步已确认的时间约束
→
3
双通道构建
原查询与“查询＋扩展文本”分别嵌入；候选项只进入检索文本，不进入时间抽取
4
窗口解析
显式查询时间优先；否则回放取源消息前沿、实时取检索开始时刻；事件锚定走两阶段检索
→
5
三路混合打分
每个通道各算 语义+词法+时间，逐记录取两通道较大值；无窗口时与旧版权重逐位一致
→
6
阈值与分组
现有总分门槛；strict 有窗口时按“确认窗内 → 时间未知 → 窗外补充”分组
7
组内排序
首末次按时间排序，其余按 分数 → created_at → id；strict 组间优先级不变
→
8
top_k 截断返回
按上述顺序取前 k 条；响应仍为 id / content / score / created_at

独立回退：LLM 关闭时常见时间规则仍运行；复杂抽取无法核验时放弃该约束； 锚点找不到时放弃事件窗口。LLM_FAILURE_MODE=fallback 下扩展失败保留有效规则约束； strict 下上游调用失败返回 503。双通道仅保证单条记录分数不低于对应裸查询分数，不保证前 k 条召回不下降。

3 · 用例走查

给定一个用例，系统到底做了什么

下面用一条本地查询走查两条链路。锚点分数、双通道得分、time_match、排名和响应来自真实 FastEmbed 向量的本次执行， 由 scripts/trace_walkthrough.py 产出（python -m scripts.trace_walkthrough 可一键复现）。 扩展文本和时间约束均为固定桩输入；时间证据经过原文校验，后续走真实检索代码。本走查不测真实 LLM 的理解或抽取能力。

用例设定

user-1 名下通过进程内 MemoryService.add 写入三条记忆（使用与 POST /set 相同的服务路径，向量已落盘）：

#记忆内容（渲染后参与嵌入的形式）距固定测量时刻角色
1[user | 2027-01-08T08:00:00.000Z] 我上周搬进了滨江路的新公寓。7 天前搬家（事件）
2[user | 2027-01-12T08:00:00.000Z] 我在新家养了一只虎皮鹦鹉，取名叫团团。3 天前目标答案
3[user | 2026-12-01T08:00:00.000Z] 住在老房子的时候我养过一只仓鼠。45 天前分心项（搬家之前）

随后平台发来检索请求：

POST /get
{"query": "搬到滨江路之后我养了什么宠物？", "user_id": "user-1", "top_k": 100}

Search 链路逐步执行

1

独立时间抽取与原文校验

事件表达通过独立入口提供相对约束。证据“搬到滨江路之后”存在于原查询中，事件短语与 after 方向均一致：

{"temporal": {"windows": [],
              "event_anchor": {"event": "搬到滨江路", "direction": "after",
                               "evidence": "搬到滨江路之后"},
              "ordering": null}}
2

独立查询扩展与双通道构建

扩展仅返回 expanded_query：“搬到滨江路之后养的宠物；新家养的动物”。两条查询文本在同一次 embed 调用中向量化：

通道A（裸查询）: "搬到滨江路之后我养了什么宠物？"
通道B（含扩展）: "搬到滨江路之后我养了什么宠物？\n查询扩展：搬到滨江路之后养的宠物；新家养的动物"

设计动机：若把扩展文本并入单一嵌入（V3 原行为），多出的词会稀释余弦与词法重合度， 把弱相关证据挤到相关度地板之下——多跳测量中这一现象让链完整率掉了 13.3 个百分点（见双通道节）。

3

读取用户记录

仅读取 user-1 的记录及其源消息时间，使用第一步已校验的约束。 时间抽取不读取候选项或扩展文本；若约束无效则沿用普通检索。

4

事件锚定：两阶段检索定位窗口边界

"之后"的参照事件不在查询里，而在库中。事件短语 "搬到滨江路" 单独向量化，与三条记录打语义+词法分：

记录锚点匹配分说明
① 搬进滨江路新公寓（7 天前）0.4975最佳命中 > 置信阈值 0.30 → 采纳为边界
② 新家养虎皮鹦鹉（3 天前）0.1869低于阈值
③ 老房子养过仓鼠（45 天前）0.1395低于阈值

边界暂以搬家记录的源消息时间代理：2027-01-08T08:00:00.000Z。 direction=after → 窗口 (边界, +∞)，不含事件自身；硬边界使窗外记录不享受近距离软衰减。 若三记录最高分仍 < 0.30，则放弃约束退回常规检索，不猜测边界。

5

三路混合打分：每通道各打分、逐记录取较大值

窗口存在 → 权重从 (0.8, 0.2) 三路归一化为 (w_sem, w_lex, w_time) = (0.6667, 0.1667, 0.1667)。 每条记录在两个通道各算一次总分（均含时间项），取较大者：

记录通道A通道Btime_match最终分 = max(A,B)排名
② 虎皮鹦鹉（3 天前，窗口内）0.48180.49891.00.49891
③ 仓鼠（45 天前，窗口外硬边界）0.33260.31400.00.33262
① 搬进滨江路（7 天前，被排除的端点）0.29680.28920.00.29683

三个读数： ① 目标记录（鹦鹉）在通道B拿到最高分——扩展改述"新家养的动物"把它的分从 0.4818 抬到 0.4989， 这就是"扩展只能提分"的数学性质在真实向量上的体现； ② 分心项（仓鼠）与查询同样语义相关，但它在搬家之前 → 硬边界 time_match=0， 时间项把目标与它的差距拉大 0.1667； ③ 搬家记录是锚点自身，“之后”排除该时刻，时间项为 0；本例 soft 模式仍按总分返回它，排第 3。

6

阈值、排序与返回

三条记录均高于 MIN_RELEVANCE_SCORE=0.20 地板；无 ordering 约束 → 按分数降序； top_k 截断后返回证据（真实响应）：

{"data": [
  {"id": "mem_707fe973885f1c8c19e3a9ac", "content": "[user | 2027-01-12T08:00:00.000Z]\n我在新家养了一只虎皮鹦鹉，取名叫团团。",
   "score": 0.49889,  "created_at": "2027-01-12T08:00:00.000Z"},
  {"id": "mem_fb123fdadef110e23088ac02", "content": "[user | 2026-12-01T08:00:00.000Z]\n住在老房子的时候我养过一只仓鼠。",
   "score": 0.332567, "created_at": "2026-12-01T08:00:00.000Z"},
  {"id": "mem_7f7636148e68f837f8dbd80a", "content": "[user | 2027-01-08T08:00:00.000Z]\n我上周搬进了滨江路的新公寓。",
   "score": 0.296764, "created_at": "2027-01-08T08:00:00.000Z"}
]}

平台的回答模型拿到这组证据即可串出答案"虎皮鹦鹉，叫团团"—— 本系统只负责把正确时间的正确证据排到前面。

如果关掉这些机制会发生什么：无时间项时三条记录按纯语义分排序，仓鼠（养宠物）与鹦鹉的 语义差距远小于 0.1667，"搬家之后"的语义会被完全忽略，答案顺序不再可靠——这正是 A/B 中 off 模式事件类 Hit@1 为 0% 的机制；无双通道时扩展文本会稀释嵌入，弱证据可能直接掉到地板之下。

4 · 核心思路一

规则优先，复杂抽取独立；绝对窗口由代码计算

直接问 LLM"最近三个月是哪段时间"会同时踩中挑战 2 和 3。本方案把时间处理切成两个职责面：

  • 抽取层：本地规则解析常见表达，复杂表达交给可用的 LLM 并核验原文证据。支持一个滚动/日历窗口或一个事件锚点，可同时带首末次排序；不支持的组合、模糊数量和未覆盖条件保守回退。
  • 解析层（纯函数，可靠且可离线单元测试）：app/temporal.py 全部函数无网络调用、无模型推理，把相对约束解析为绝对毫秒窗口。

四种受控约束类型

内部约束结构；LLM 窗口/事件额外必需 evidence，排序必需 ordering_evidence
类型结构例句解析结果
滚动窗口{"kind":"rolling","unit":"day|week|month|year","amount":N,"direction":"past|future"}"最近三天"[锚点−3d, 锚点]，天/周用 timedelta，月/年必须日历运算
日历窗口{"kind":"calendar","unit":"...","offset":N}"上个月"锚点所在月起步移 offset=−1，即整月窗口；"上上周"= week/−2
事件锚点{"event":"搬到上海","direction":"before|after"}"搬到上海之前我住哪"事件短语须对应原文；两阶段检索以源消息时间代理边界，“之前/之后”均排除事件自身
首末次排序{"ordering":"earliest|latest"}"我第一次提到 Aurora"不产生窗口，只改变候选排序；时间未知排最后

TEMPORAL_EXTRACTION_MODE=hybrid 默认采用规则优先与复杂抽取；rules 仅用规则，off 关闭抽取。 此配置独立于 LLM_SEARCH_EXPANSION，无 LLM 也能解析常见表达。 复杂查询同时开启扩展时可能需要两次 LLM 调用；规则完整命中不增加时间抽取调用。

查询参考时间：显式查询时间优先，区分回放与实时模式

相对窗口必须有一个"现在"作参照。2026-10-02 修订后， TEMPORAL_REFERENCE_MODE 明确区分历史回放与实时查询，默认 replay。 resolve_anchor 的选择规则是：

#锚点来源条件代码
1显式查询时间内部 search 调用传入时优先；HTTP 字段不变query_time_ms / query_time
2a对话前沿：该 user 最大有效源消息时间未指定查询时间且模式为 replaymax(source_timestamp) / conversation_frontier
2b本次检索开始时刻未指定查询时间且模式为 realtime；在 LLM / 向量调用之前捕获request_time_ms / request_time
3无法确定回放缺少源消息时间且无显式查询时间，放弃相对窗口None / unavailable

记录时间只采用有效的 source_timestamp，缺失或不可解析时保持未知， 不使用 created_at 补齐，避免补录时间改变历史查询窗口。 全部消息时间未知时退回普通排序。参考时间来源保存在检索上下文及调试日志中。 消息时间不等同于事件发生时间；正文事件时间抽取属于后续步骤。

日历运算的确定性细节

  • 月/年窗口用 _shift_months 日历平移，月末日期按目标月天数收敛（5 月 31 日 − 1 月 → 4 月 30 日；2 月按闰年收敛）——单元测试固定覆盖；
  • 周窗口以周一为起点；日/周用 timedelta；拒绝用 30 天近似一个月；
  • 过去滚动窗口为 [参考时刻−长度, 参考时刻]，包含最新记录；未来滚动窗口为 [参考时刻, 参考时刻+长度)。
  • 日历窗口保持 [周期起点, 下一周期起点)，按 UTC 计算；事件之前/之后均排除事件时刻。端点是否包含由 TemporalWindow 显式保存。

5 · 核心思路二

软打分：奖励匹配而不是惩罚失配

解析出窗口后，时间进入打分函数。默认软模式下，每个通道的总分是三路加权和：

# app/service.py  _score_record + 双通道取最大
score(通道) = w_sem·语义余弦 + w_lex·词法重合 + w_time·time_match
final = max(score(通道A), score(通道B))

# 有时间窗口时三路归一化（默认 0.8/0.2/0.2 → /1.2 → 0.667/0.167/0.167）
# 无时间窗口时退回二元权重 (0.8, 0.2) + 0.0 —— 与旧实现逐位一致

time_match 的四条规则（temporal.py time_match）

情形得分设计理由
窗口内1.0满奖励
窗口外（软窗口）exp(−ln2 · 距离天数 / 半衰期)离窗口一天之遥和一年之遥不该同罪；默认半衰期 30 天，距离一个半衰期得分 ≈ 0.5
时间未知0.5严格模式中属于第二组，仍受现有分数门槛与 top_k 限制，不计作确认窗内
窗口外（硬边界，事件锚定）0"搬家之前"语义上明确不含搬家之后，窗外不享受近距离软衰减

软 / 严格两档

TEMPORAL_MODE=soft（默认）

时间只参与加权。窗口外记录仍可凭高语义分入围——适合时间信号本身可能不可靠的场景，代价是分心项偶尔仍会入围（但排序被压低）。

TEMPORAL_MODE=strict

按“确认窗内 → 时间未知 → 窗外补充”分组；组内按分数或首末次排序，最后统一截取 top_k（_rank_strict_temporal_candidates）。分组不依赖返回数量，补充记录不会越过窗内记录；仍保留不足时补充语义，并非禁止所有窗外记录。

适用边界：软模式按加权总分排序，严格模式保证组间优先级。 当前总分门槛仍在时间加分之后执行，时间权重会影响入围，不能据此保证不丢失答案；相关性门槛与时间排序解耦属于后续优化。

6 · 核心思路三

程序化防御：每一条 LLM 时间声明都要被验证

提示词约束不构成保证。所有可靠性都来自可测试的代码防线，按约束生命周期排布：

防线链：一条时间约束从产生到生效要过的每一关（走查用例中的实际数值见第 3 节第 4 步）
#防线位置不过时
1规则与独立抽取：规则完整命中即采用；复杂抽取只读原查询并要求证据，不换算绝对日期_query_temporal / TEMPORAL_EXTRACTION_PROMPT不完整或不支持的约束回退
2schema 白名单：kind/unit/amount/offset/direction/ordering 逐字段校验，非法值整条丢弃（bool 被显式排除，不会当 1 用）parse_temporal返回 None，按无约束处理

4锚点置信度：事件短语定位到的最佳记录分数 < TEMPORAL_EVENT_ANCHOR_MIN_SCORE(0.30) 时放弃约束_resolve_event_anchor_window退回常规检索，不猜测边界
5总开关旁路：TEMPORAL_MODE=off 时打分路径与旧版逐位一致service.py 全链路—（回归安全阀）

事件锚定：两阶段检索

“搬家之前我住哪”的边界由事件记录的源消息时间代理，尚未抽取正文事件发生时间。解析分两步：

# service.py  _resolve_event_anchor_window
① 事件短语（"搬到上海"）单独向量化
② 与该 user 全部记录算 语义+词法 分（无时间项），取最高分记录的有效源消息时间为边界
   · direction=before → 窗口 (-∞, 事件时间)  硬边界（事件本身不含在"之前"里）
   · direction=after  → 窗口 (事件时间, +∞)  硬边界（事件本身不含在“之后”里）
③ 最高分 < 0.30 → 放弃约束，退回常规检索（不猜边界）

硬边界语义写进类型：窗外记录一律 0 分时间项，不因"距离窗口边界近"获得软衰减—— before 硬边界来自初版修复，2026-10-03 进一步统一 after 排除事件端点；事件是否成立、多次发生消歧仍未实现。

7 · 查询表达层

双通道查询：让扩展只能提分，永不稀释

多跳测量门（15 例桥接实体场景 × 每例约 180 条程序化干扰记忆）发现一个反直觉事实： V3 把扩展文本并入单一嵌入，会让余弦与词法重合度被稀释，把弱相关证据挤到 MIN_RELEVANCE_SCORE 地板之下——在多跳链式查询上，链完整率因此掉了 13.3 个百分点。 平台协议下系统只负责返回证据、由平台的回答模型串联多跳，因此"证据掉到地板之下"就是链断裂。

设计：max(通道A, 通道B)

final(record) = max( score(裸查询, record), score(裸查询+扩展文本, record) )   # 均含时间项

三条数学性质由单元测试锁定（test_dual_channel.py）： ① 扩展只能提分——max ≥ 裸查询通道，弱证据永远不会因扩展掉分或掉出地板； ② 无扩展文本时开关无感——LLM 关闭或扩展为空，打分与旧版逐位一致； ③ QUERY_DUAL_CHANNEL=false 精确回退 V3 单通道行为，一行配置即可 A/B 对照。 成本：扩展存在时每查询多一次嵌入与一倍打分（无额外 LLM 调用）。

实证：三条件同库对照（15 例多跳链式场景，chain@k = 全部跳证据都在 top-k 内）

数据源 data/multihop_report.json；三种条件共享同一记忆库，只差查询表达与通道开关
查询条件chain@10chain@20chain@100hop1/hop2 召回过地板池均值
裸查询（无扩展，检索下界）80.00%80.00%86.67%1.00 / 1.0019.9 条
双通道（默认开启）86.67%86.67%93.33%1.00 / 1.0031.8 条

结论：双通道在所有指标上 ≥ 裸查询（扩展的改述收益被保留），且在所有指标上严格优于 V3 单通道 （稀释伤害被免疫）；唯一代价是过地板的证据池更大（19.9 → 31.8 条），在官方 top_k=100 的设定下可接受。

测量门的附带裁决：不做子查询扇出、不做实体图层

同一批数据先回答了"要不要为多跳建图结构"：裸查询下桥接实体召回率 100%（hop1 全部排在 rank 1-6）、 链完整率 86.67% 已过 85% 阈值——多跳丢证据的主因是相关度地板而非桥接检索能力， 昂贵的图结构（Mem0g/Zep 路线）被数据否决。剩余缺口（hop3 弱语义末端跳）的修复路径在写入端增强而非检索端。

9 · 工程底座

与算法同等重要的四条契约

幂等与冲突检测

request_id 主键 + payload_hash（规范化 JSON 的 SHA-256）：同 ID 不同内容 → 409 冲突；同 ID 已完成 → 幂等成功；处理中超时（默认 300s）→ 允许安全重试。失败请求显式 mark_failed，不留下永久卡死状态。

user_id 严格隔离

检索只加载当前 user_id 的记录（带索引的 SQL 过滤 + 内存余弦），简化接口落入独立本地空间。跨用户检索在数据路径上不存在，不靠过滤兜底。

写入可见性契约

Add 在向量与时间戳事务提交后才返回 200——"可检索"是持久化之后的属性，不是 aspirational 的。WAL + synchronous=FULL + BEGIN IMMEDIATE 单写者串行化。

数据保留与攻击面

启动时按写入时间清理 30 天前批次（"评测数据 30 天内删除"的保守实现）；Swagger/OpenAPI 默认关闭，公网部署强制 MEMORY_API_KEY（Bearer/Token/X-Api-Key 三种传法，常数时间比较），/health 按契约免鉴权。

11 · 边界与披露

这套方案不承诺什么

  • oracle ≠ 端到端：A/B 固定约束仅测打分层；--llm real 才运行生产抽取路径。现有一致率仅比较约束类型，异常仍被排除出质量指标分母，不能证明字段级或总体端到端质量。
  • 本轮范围：日历时区仍为 UTC，消息时间仍代理事件边界；不支持的复合时长、多窗口与否定窗口保守回退。事件事实判定、相关性门槛解耦、事实更正和分块不属于本轮修改。
  • 证据在地板下检索端无解：弱语义证据（如"最早排序"一例、多跳 hop3）不过 MIN_RELEVANCE_SCORE 时，检索端任何排序逻辑都救不回——这是写入端增强（enrichment）的职责边界。
  • 测量自身的局限：两个面板的数据集为人工合成（多跳干扰记忆由模板生成），模拟的是机制压力而非评测分布；数字用于设计决策与回归，不外推为正式评测成绩。
  • 不含任何评测金标：系统无数据集硬编码；调参只能用公开材料；禁止用 benchmark 泄漏样本、人工实时答题或提示注入调整系统。
  • 合规模式区分：官网 Full 清单当前要求 gpt-4o-mini；DeepSeek 仅用于本地实验与方法验证，其运行结果不冒充合规勾选。不能发送评测数据到第三方时保持 LLM_PROVIDER=none。
  • 向量模型维度变更：换 EMBEDDING_MODEL 后旧向量维度不一致，须换新库或离线重建，不能混用分数（检索端对维度不匹配记录跳过而非返回错分）。
  • 规模边界：SQLite + 内存余弦适合按 user 隔离的单样本规模；更大规模需独立向量库。
