# Agent Memory V3：时间感知检索技术方案

## 1. 方案定位

V3 在**不改变写入路径、存储结构与 API 契约**的前提下，为检索管线引入时间约束。2026-10-03 修订后，常见表达由规则解析，复杂表达通过独立 LLM 入口抽取并核验原文证据；绝对窗口计算、打分与排序由确定性代码完成。

- **解决的目标问题**：长期多轮对话中的时间序列推理——"上个月说过什么""搬家之前住哪""第一次提到 X 是什么时候"。
- **三条设计目标（按优先级）**：
  1. 改善时间限定查询（本次固定样本 oracle A/B：Hit@1 20% → 80%，见 §6.2；不代表真实 LLM 端到端成绩）；
  2. 无时间约束时保留原打分路径（回归断言见第 6 节）；
  3. 不可信约束可回退；严格模式补充证据不能越过确认满足时间约束的证据。

## 2. 问题背景：V2 的时间盲区

V2 的写入端已经相当完备：

- 消息自带 `timestamp` 随记录持久化（`memories.source_timestamp`）；
- 写入增强提示词（V2）明确约束"时间及变化：不得把过去状态写成当前状态"；
- `SearchHit` 返回 `created_at` 供上层推理。

但**检索端完全不用时间**：

- 打分只有语义余弦 + 词法重合（默认 0.8 / 0.2）；
- "上个月""搬家之前"只作为普通文本参与嵌入——语义模型无法区分"我住北京"和"我上个月说住北京"这两条记忆谁回答"现在住哪"；
- 默认排序的 `created_at` 升序平局，与"最近一次"类查询意图相反。

后果：同主题、不同时间的多条记忆（长对话的常态）在时间限定查询下近乎随机竞争——A/B 基线（V2 行为）在事件类查询上 **Hit@1 = 0%**。

## 3. 核心设计思想

### 3.1 抽取与解析分离

时间抽取只处理相对表达，不要求模型猜测当前日期。`app/temporal_extraction.py` 先解析“昨天、今天、本月、过去三天”等中英文常见表达；规则无法完整解析时，`hybrid` 模式才调用 LLM。支持以下四类结构，绝对窗口由 `app/temporal.py` 计算：

| 约束类型 | 查询示例 | 结构（temporal 字段） |
| --- | --- | --- |
| 滚动窗口 rolling | "最近三个月" | `{"windows":[{"kind":"rolling","unit":"month","amount":3,"direction":"past"}]}` |
| 日历窗口 calendar | "上个月""去年" | `{"windows":[{"kind":"calendar","unit":"month","offset":-1}]}` |
| 事件锚点 event_anchor | "搬到上海之前" | `{"event_anchor":{"event":"搬到上海","direction":"before"}}` |
| 首末次排序 ordering | "第一次 / 最近一次" | `{"ordering":"earliest"}` / `"latest"` |

日历运算的边界由代码保证（如 5 月 31 日 − 1 个月收敛到 4 月 30 日、跨年、闰年），模型不参与。

表中为内部约束结构。LLM 输出的窗口、事件还必须含原查询片段 `evidence`，排序必须含 `ordering_evidence`；规则生成的内部约束不经过 LLM。一次查询只接受一个相对窗口或一个事件锚点，可以同时带排序；不支持的多窗口与组合条件保守回退。

### 3.2 程序化防御

延续本项目"提示词约束不等于程序化保证"的哲学，时间约束有三道程序防线：

1. **结构校验**：`parse_temporal` 核验类型、单位、数量、范围和方向；布尔值不充当数量，缺失或非法方向不再改为 `past`，未知字段或不支持的组合整条丢弃；
2. **原文校验**：`parse_grounded_temporal` 要求证据出现在原查询中，窗口各字段与证据一致，事件短语及前后关系有对应原文，排序方向一致；检测到未覆盖的时间限定时，不只采用部分约束。模糊数量、否定窗口与多窗口不擅自转成单个确定窗口；
3. **未知时间**：缺少有效源消息时间的记录保持未知，`time_match` 固定 0.5。严格模式中属于独立补充组，排在确认窗内记录之后，仍受现有分数门槛与 `top_k` 限制。

### 3.3 分级降级链

```
LLM 关闭 / 查询扩展关闭 ──► 常见时间规则仍可独立运行
复杂抽取调用失败 ──► LLM_FAILURE_MODE=fallback 时丢约束；strict 时返回 503
查询扩展调用失败 ──► fallback 时保留已解析的时间约束，使用原查询
结构 / 原文校验不通过 ──► 丢弃约束，退回普通检索
事件锚点不可解析 ──► 放弃约束（不猜测窗口边界）
回放无源消息时间且无显式查询时间 ──► 放弃相对窗口；全部时间未知时沿用普通排序
日历平移超出支持范围 ──► 放弃相对窗口，保留可用的独立约束
TEMPORAL_MODE=off ──► 与 V2 行为逐位一致
```

每一级都有单元测试锁定，其中"无约束路径与 V2 分数逐位一致"由专门的回归断言保证。

## 4. 查询处理管线

```
query
  ├─ 捕获本次检索开始时刻（供 realtime 模式使用）
  ├─ 独立时间入口 _query_temporal（只读原查询）
  │    ├─ 常见规则完整命中 → 结构化约束
  │    └─ hybrid 且 LLM 可用 → 复杂抽取 → 字段及原文证据校验
  ├─ 可选 LLM 查询扩展（只输出 expanded_query 文本）
  ├─ 查询嵌入（原查询 + 候选项 + 扩展文本）
  └─ fetch_by_user（读取记录，含 source_timestamp）
        ↓
时间上下文解析（service._resolve_temporal_context）
  ├─ 查询参考时间：显式 query_time_ms 优先；否则按 replay / realtime 模式选择
  │    ├─ replay：该 user 的 max(有效 source_timestamp)；无可信源时间则不解析相对窗口
  │    └─ realtime：检索开始时刻，不受后续 LLM / 向量调用耗时影响
  ├─ 事件锚点：两阶段检索定位事件记录 → 硬边界窗口
  └─ 相对窗口：确定性日历运算 → 软衰减窗口
        ↓
三路加权打分：score = w_sem·语义 + w_lex·词法 + w_time·time_match
  ├─ 窗口内：1.0
  ├─ 软衰减窗口外：exp(−ln2 · 距离天数 / 半衰期)
  ├─ 事件硬边界窗口外：0.0（事件"之前/之后"语义是硬的）
  └─ 记录无时间戳：0.5（中性）
        ↓
现有总分门槛：只保留达到 MIN_RELEVANCE_SCORE 的候选
        ↓
[strict 且有窗口] 分组：确认窗内 → 时间未知 → 窗外补充
排序：各组内部 ordering=earliest/latest 时按时间排；否则 (−score, created_at, id)
[soft 或无窗口] 沿用普通排序，不分组
        ↓
top_k 截断
```

## 5. 核心组件

### 5.1 独立查询扩展与时间抽取（`app/prompts.py`、`app/llm.py`）

- `QUERY_EXPANSION_PROMPT_V3` 只输出检索辅助文本，保留主体、极性、否定和时间限定，不回答问题。
- `TEMPORAL_EXTRACTION_PROMPT` 只接收原查询，输出相对约束和对应原文证据；不接收候选项，不使用扩展内容。
- `TEMPORAL_EXTRACTION_MODE=off/rules/hybrid` 控制时间抽取，独立于 `LLM_SEARCH_EXPANSION`。关闭 LLM 时，`rules` 与 `hybrid` 均能解析受支持的常见表达。
- 复杂查询同时开启扩展时可能产生两次 LLM 调用；规则完整命中不调用时间抽取 LLM。模糊数量、无法证明或无法完整表示的约束返回 `None`。

### 5.2 时间窗口引擎（`app/temporal.py`，纯函数、零外部依赖）

| 组件 | 职责 |
| --- | --- |
| `TemporalWindow` | 显式 `start_inclusive` / `end_inclusive` 及 `hard_boundary` 标志 |
| `parse_temporal` | LLM 输出的受控解析与校验 |
| `resolve_relative_window` | 滚动/日历窗口的确定性计算（含月末收敛） |
| `TemporalReference` | 查询参考时间与来源：query_time / conversation_frontier / request_time / unavailable |
| `effective_time_ms` | 只验证源消息时间；缺失或无效时返回 None，不解析 created_at |
| `resolve_anchor` | 显式查询时间优先；回放取源消息前沿，实时取检索开始时刻 |
| `time_match` | 时间匹配分：1.0 / 软衰减 / 硬边界 0.0 / 未知 0.5 |
| `query_mentions_temporal` | 复杂抽取调用门控与剩余时间信号检查；命中本身不证明约束正确 |

**窗口端点约定**（2026-10-03 修订，日历仍使用 UTC）：

| 表达 | 区间 | 端点规则 |
| --- | --- | --- |
| 过去 N 天/周/月/年 | `[参考时刻−长度, 参考时刻]` | 包含查询锚点，避免排除最新记录 |
| 未来 N 天/周/月/年 | `[参考时刻, 参考时刻+长度)` | 保持原未来窗口规则 |
| 昨天/本月/上周等日历窗口 | `[周期起点, 下一周期起点)` | 相邻周期不重叠 |
| 事件之前 / 之后 | `(-∞, 事件时刻)` / `(事件时刻, +∞)` | 均排除事件自身；窗外时间分为 0 |

被排除的整数毫秒端点与窗口的距离至少为 1ms，不再在 `contains=False` 时仍获得满额软时间分。

**查询参考时间与消息时间分开定义**（2026-10-02 第一步修订）：

1. 内部 `MemoryService.search(..., query_time_ms=...)` 指定查询时间时优先使用；HTTP schema 不新增字段。
2. 默认 `TEMPORAL_REFERENCE_MODE=replay`：取当前 user 的最大有效源消息时间。全部缺失时不以入库时间或服务器时钟补齐，而是放弃相对窗口，退回普通检索。
3. `TEMPORAL_REFERENCE_MODE=realtime`：取进入 `search` 时捕获的时刻；即使历史记录很旧，也以本次实际查询时刻解释“上个月”。

记录的 `source_timestamp` 是消息时间，缺失或超出可解析范围时保持未知；`created_at` 可能是入库时间，不参与参考时间、时间打分或首末次排序。所有消息时间未知时沿用普通排序。显式查询时间需为非负、可解析的整数毫秒时间戳；非法值在参考时间解析时抛出 `ValueError`。参考时间来源保存在检索上下文并写入调试日志。数据库结构和写入逻辑不变，无需重建向量。

### 5.3 检索集成（`app/service.py`）

- **权重归一化**：默认三路原始权重 (0.8, 0.2, 0.2)，窗口激活时归一化为 (0.667, 0.167, 0.167)；无窗口时退回 (0.8, 0.2, 0.0)，分数与 V2 逐位一致。
- **事件锚定两阶段检索**：Pass 1 用事件短语做一次小规模检索，以最高分命中记录的源消息时间代理事件边界；源时间未知或置信度不足时放弃该事件约束。正文中的事件发生时间抽取属于后续步骤，本次未实现。
- **硬边界**：事件“之前”和“之后”均排除事件自身；窗外记录的时间分为 0，不享受近距离软衰减。是否返回还取决于模式、总分门槛和返回数量。
- **首末次排序**：在通过现有总分门槛的候选内按时间排序（earliest 升序 / latest 降序）；有严格窗口时只在各组内部排序。
- **严格模式**：`_rank_strict_temporal_candidates` 按“确认窗内、时间未知、窗外补充”分组，各组内部排序后统一截断。分组与 `top_k` 无关；同一候选集和约束下，增大返回数量保持已返回前缀不变。不保证返回满额，也不把未知时间当作确认窗内。

### 5.4 配置项

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `TEMPORAL_MODE` | `soft` | `off` 关闭 / `soft` 加权参与打分 / `strict` 确认窗内→未知→窗外补充 |
| `TEMPORAL_EXTRACTION_MODE` | `hybrid` | `off` 关闭抽取 / `rules` 本地规则 / `hybrid` 规则优先，复杂表达交给可用的 LLM；独立于查询扩展开关 |
| `TEMPORAL_REFERENCE_MODE` | `replay` | `replay` 按源消息时间回放 / `realtime` 按本次检索开始时刻；显式 query_time_ms 优先 |
| `TEMPORAL_WEIGHT` | `0.20` | 时间项权重（与 0.8/0.2 三路归一化） |
| `TEMPORAL_DECAY_HALF_LIFE_DAYS` | `30` | 软衰减窗口外距离的半衰期 |
| `TEMPORAL_EVENT_ANCHOR_MIN_SCORE` | `0.30` | 事件锚点定位的最低置信分 |

## 6. 安全与回归保证

- **API 契约零变更**：响应 schema 不变（`StrictModel extra="forbid"` 未动），`main.py` 无改动；
- **写入路径零改动**：幂等 claim、user_id 隔离、enrichment V2 全部保持；
- **逐位回归**：无时间约束时打分公式与 V2 完全一致（专门的 bit-exact 断言）；
- **未知时间保持未知**：不回退入库时间；已有有效窗口时，未知记录的时间项为 0.5；
- **不可信约束丢弃**：结构、字段与原文证据校验拒绝不一致的 LLM 输出；这不等于已证明模型理解所有自然语言时间表达。

- 【已验证】20 个字段专项中有 5 处字面差异：`this past week`、`most recent` 未形成有效约束；其余涉及旧 oracle 的自然周/滚动周、一个月/30天及事件短语粒度，不能都判为模型错误。5 个新增常见表达均走规则并与期望一致。
- 原始报告位于 `data/temporal-real-2026-10-04/`；完整证据、错误归因与适用边界见 [真实 LLM 验证记录](v3-real-llm-validation-2026-10-04.md)。当前仍需补足两个英文表达的结构提示及证据校验覆盖。

## 7. 历史实验记录（初版 V3，当前复测见 §6.2、§6.3）

以下数字保留原实验记录，不作为当前环境复测结果；向量运行时与代码修订可能影响结果。

### 7.1 实验设计

- **数据集**：15 条手工构建的时间歧义场景（`tests/fixtures/temporal_ab_cases.jsonl`）——每个场景同一 user 名下多条同主题、不同时间戳的记忆 + 一条带时间限定的查询；目标答案（target）与同主题错误时间记录（distractor）的关键词必须各自唯一出现在对应记忆中。类型分布：rolling×5、event×5、ordering×5，中英混合。
- **指标**：Hit@1 / Hit@5 / MRR@5 / 目标压过分心项比例。
- **方法学（oracle 分层）**：时间约束由数据集内置的期望值（oracle）直接提供，隔离抽取层与打分层，测量约束给定时的排序表现。`--llm real` 运行生产抽取路径；现有类型签名一致率不能代表字段正确率，也不能与排序增益相乘推导端到端增益。
- **运行方式**：进程内全链路（真实 FastEmbed 多语言向量 + MemoryService），`TEMPORAL_MODE=off/soft` 双实例对比。

### 7.2 结果（打分层，真实向量）

| 指标 | off（= V2 行为） | soft（= V3） | 提升 |
| --- | --- | --- | --- |
| Hit@1 | 33.33% | **80.00%** | +46.7pp |
| Hit@5 | 80.00% | **100%** | +20.0pp |
| MRR@5 | 0.5556 | **0.9000** | +0.34 |
| 目标压过分心项 | 53.33% | **100%** | +46.7pp |

分类型（off → soft 的 Hit@1）：

| 查询类型 | off | soft | 说明 |
| --- | --- | --- | --- |
| rolling（最近N天/周/月） | 60% | 100% | 同主题旧记录彻底压不过目标 |
| ordering_earliest（第一次） | 50% | 100% | 显式时间排序替代语义平局 |
| ordering_latest（最近一次） | 33% | 100% | 修正了 off 升序平局的方向性错误 |
| event_before / event_after | 0% | 67% / 0% | Hit@5 均达 100%，rank1 残留问题见 7.3 |

### 7.3 实验发现的两个问题

1. **事件记录边界软衰减（已修复）**：事件锚定窗口中，事件记录本身落在边界上，按距离衰减拿到接近满分的 time_match，导致事件记录常排在真正答案之前。V3.1 将事件窗口改为硬边界（窗外 0 分），由白盒测试锁定。
2. **锚点记录自指匹配（已知，待下一版）**：查询包含事件短语（"搬到滨江路之后养了什么宠物"），事件记录与查询语义重叠天然最高，即使 time 项归零仍可能占据 rank1（本轮 15 例中 3 例，答案均在 rank2，Hit@5 = 100%）。修复方向是锚点记录降权策略，但存在"锚点记录本身就是答案"的反例（如"搬家之后我住哪"），需要单独设计判别逻辑。

## 9. 已知限制与后续方向

1. **真实 LLM 覆盖仍有限**：已完成 §6.3 的小样本实测，发现两个英文表达覆盖缺口；尚无充分数据证明整体字段正确率；
2. **权重未调参**：`TEMPORAL_WEIGHT=0.20` 与 30 天半衰期为工程默认值，未做网格标定；
3. **strict 模式的证据范围**：已有确定性服务测试、HTTP 契约测试及 4 个真实模型/向量专项；A/B 只比较 off/soft，未提供 strict 大样本质量数据；
4. **锚点自指问题**：见 7.3，需专门设计；
5. **复杂表达覆盖**：多窗口、否定窗口、不支持的复合时长与部分可解析表达保守回退；原文证据校验不能替代事件事实判定；
6. **日历窗口的锚点敏感性**："上个月"依赖对话前沿落在正确月份，前沿漂移时可能错位（数据集因此以 rolling/event/ordering 为主）。
